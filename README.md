# Booking service

Простой HTTP JSON API для номеров отеля и бронирований. Python 3.13, Django 5.2 LTS,
Django REST Framework, PostgreSQL 17, psycopg 3. Зависимости зафиксированы в `poetry.lock`.
Авторизация и графический интерфейс не требуются.

## Быстрый запуск

Нужны Docker и Docker Compose v2. Сначала создайте локальный `.env`
со случайным паролем PostgreSQL и ключом Django (генератор использует стандартную библиотеку Python 3):

```bash
python scripts/init_env.py
```

Генератор не перезаписывает существующий `.env` и не выводит секреты в терминал.
Без Python можно скопировать `.env.example` в `.env` и самостоятельно заменить
обе заглушки секретов. `.env.example` содержит только шаблон; `.env` исключён из Git
и Docker-контекста. Пароль БД и ключ Django обязательны, значений по умолчанию в коде нет.

Запуск:

```bash
docker compose up --build -d --wait
curl http://localhost:9000/healthz
```

API доступен на `http://localhost:9000`, интерактивная документация —
`http://localhost:9000/docs`, OpenAPI — `/openapi.json`.
Порты 9000 и 15432 должны быть свободны. В PowerShell можно использовать `curl.exe`.
PostgreSQL опубликована на 15432, чтобы не конфликтовать с локальной БД на 5432;
порт можно изменить через `POSTGRES_PORT` в окружении Compose или файле `.env`.

Схема из `db/schema.sql` применяется автоматически при первом запуске PostgreSQL
с пустым томом. Повторный запуск не пересоздаёт таблицы.
Данные хранятся в именованном томе `postgres_data` и сохраняются после рестарта
и `docker compose down`.

```bash
docker compose logs -f api
docker compose restart api db
docker compose down
```

`docker compose down -v` **удаляет данные БД**. Контейнеры публикуют порты только на `127.0.0.1`.
Compose читает настройки из локального `.env` и передаёт их контейнерам через окружение.
Внутри Docker используются хост `db` и порт `5432`; локальный Django берёт хост
и опубликованный порт из `.env`.

Для существующего тома изменение `POSTGRES_PASSWORD` в `.env` само по себе не меняет
пароль роли PostgreSQL. Сначала смените пароль через `ALTER ROLE`/`psql \password`,
обновите `.env`, затем пересоздайте контейнеры через `docker compose up -d`.

## Локальная разработка

Нужны Python 3.13 и Poetry 2.2.1. PostgreSQL можно оставить в Docker:

```bash
python scripts/init_env.py
docker compose up -d db
poetry sync
```

Настройки автоматически загружаются из `.env`; уже заданные переменные окружения
имеют приоритет. Команда одинакова для Linux/macOS и PowerShell:

```bash
poetry run python manage.py runserver 127.0.0.1:9000
```

Для собственной PostgreSQL заполните `POSTGRES_*` в `.env`, создайте пустую БД
и примените схему один раз. Подставьте значения HOST, PORT, USER и DATABASE_NAME
из вашей конфигурации; `-W` запрашивает пароль интерактивно:

```bash
psql -h HOST -p PORT -U USER -d DATABASE_NAME -W -v ON_ERROR_STOP=1 -f db/schema.sql
```

При необходимости локальному Django можно задать `DATABASE_URL` в окружении или `.env`
вместо отдельных `POSTGRES_*`; специальные символы логина и пароля в URL должны
быть URL-кодированы. Для Compose используются отдельные переменные `POSTGRES_*`,
поэтому пароли с `@`, `:`, `/` не требуют сборки или кодирования URL.

Пользователю БД нужно право создать расширение `btree_gist` (либо его заранее
устанавливает администратор). Миграции не используются. Django-модели объявлены
с `managed=False` и работают с таблицами из SQL-файла. Выполнять `manage.py migrate`
или пересоздавать существующий том при переходе на Django не нужно.

В контейнере приложение запускается через Gunicorn: один WSGI-процесс, восемь потоков.
`runserver` используется для локальной разработки. `DJANGO_ALLOWED_HOSTS` задаёт
разрешённые имена хостов через запятую (по умолчанию localhost и loopback).
API не использует сессии и авторизацию; `DJANGO_SECRET_KEY` читается из `.env`
или окружения и сохраняется между перезапусками.

## Методы API

POST-запросы принимают `application/x-www-form-urlencoded` (как в ТЗ) или
`application/json`. Неизвестные и повторяющиеся поля тела отклоняются.
Все ответы API, включая ошибки, возвращаются в JSON.

| Метод | URL | Параметры | Ответ |
| --- | --- | --- | --- |
| POST | `/rooms/create` | `description`, `price` | `201`, `{"room_id":24}` |
| POST | `/rooms/delete` | `room_id` | `200`, `{"status":"ok"}` |
| GET | `/rooms/list` | `sort_by`, `order` (необязательны) | `200`, массив номеров |
| POST | `/bookings/create` | `room_id`, `date_start`, `date_end` | `201`, `{"cbooking_id":1444}` |
| POST | `/bookings/delete` | `booking_id` | `200`, `{"status":"ok"}` |
| GET | `/bookings/list` | `room_id` | `200`, массив броней |
| GET | `/healthz` | — | `200`, `{"status":"ok"}`, или `503`, если БД недоступна |

### Номера

Описание: от 1 до 10000 символов после удаления пробельных символов по краям.
Цена за ночь: от `0.01` до `9999999999.99`, не более двух значащих знаков после
запятой. Входная цена может быть JSON-числом или строкой; разделитель — точка.
В ответах цена — десятичная строка с двумя знаками, чтобы клиенты сохраняли точность.

```bash
curl -X POST http://localhost:9000/rooms/create \
  --data-urlencode 'description=Двухместный номер с видом на море' -d 'price=3500.50'
# {"room_id":24}

curl -X POST http://localhost:9000/rooms/create \
  -H 'Content-Type: application/json' \
  -d '{"description":"Люкс","price":"5500.00"}'

curl 'http://localhost:9000/rooms/list?sort_by=price&order=asc'
# [{"room_id":24,"description":"Двухместный номер с видом на море",
#   "price":"3500.50","created_at":"2026-11-08T12:00:00Z"}, ...]

curl -X POST http://localhost:9000/rooms/delete -d 'room_id=24'
# {"status":"ok"}
```

Сортировка: `sort_by=price|created_at`, `order=asc|desc`.
По умолчанию `created_at`, `asc`. При одинаковых значениях используется ID в том
же направлении, поэтому порядок детерминирован. Удаление номера атомарно удаляет все его брони.

### Бронирования

```bash
curl -X POST http://localhost:9000/bookings/create \
  -d 'room_id=24' -d 'date_start=2026-12-30' -d 'date_end=2027-01-02'
# {"cbooking_id":1444}

curl 'http://localhost:9000/bookings/list?room_id=24'
# [{"booking_id":1444,"date_start":"2026-12-30","date_end":"2027-01-02"}]

curl -X POST http://localhost:9000/bookings/delete -d 'booking_id=1444'
# {"status":"ok"}
```

Даты — строго `YYYY-MM-DD`, календарно валидные, годы `0001–9999`.
Окончание строго позже начала. Список броней отсортирован по дате начала по возрастанию,
затем по ID. Для существующего номера без броней возвращается `[]`.

### Ошибки

Формат: `{"error":"текст ошибки"}`.
Ошибки валидации содержат имя поля и понятное сообщение, например
`{"error":"description: This field may not be blank."}`.

| Код | Причина |
| --- | --- |
| 400 | Невалидные поля, даты, ID, сортировка, тело запроса или неразрешённый Host |
| 404 | Номер, бронь или маршрут не существует |
| 405 | Неподдерживаемый HTTP-метод |
| 406 | Запрошен неподдерживаемый формат ответа в Accept |
| 409 | Даты пересекаются с другой бронью этого номера |
| 413 | Тело запроса больше 1 МиБ |
| 415 | Неподдерживаемый Content-Type |
| 500 | Внутренняя ошибка; детали записываются в серверный лог |
| 503 | БД недоступна при проверке `/healthz` |

## Принятые решения

- День выезда не входит в бронь: интервал `[date_start, date_end)`.
  Брони `20–25` и `25–27` допустимы, `20–25` и `23–27` — конфликтуют.
- Проверка доступности реализована ограничением PostgreSQL `EXCLUDE USING gist`
  с `btree_gist`. Оно защищает от двойной брони даже при конкурентных запросах,
  без небезопасной последовательности «проверить, затем вставить».
- Ключ `cbooking_id` при создании сохранён буквально по примеру ТЗ; в списке
  и при удалении используется `booking_id`.
- Цена хранится целым числом копеек (`BIGINT`), вход обрабатывается через `Decimal`.
  Валюта одна, условная: мультивалютность не входит в задачу.
- Прошедшие даты разрешены: ограничения относительно текущей даты в ТЗ нет.
- Повторное удаление отсутствующего объекта возвращает `404`.
- Время добавления формирует БД; API использует UTC. ID — положительные 64-битные числа.
- Каталог общий для одного отеля. Пагинация и отдельная сущность отеля не вводятся.
- Индексы `(price_cents, id)`, `(created_at, id)` обслуживают сортировку номеров;
  `(room_id, date_start, id)` — список броней и каскадное удаление.
  Сортировка допускает только фиксированные поля; значения SQL передаются параметрами.
- Работа с данными реализована через Django ORM. Django управляет пулом psycopg
  (до 10 соединений на процесс, `CONN_MAX_AGE=0`). Операции выполняются в autocommit
  или `transaction.atomic()`; ограничение пересечений остаётся в PostgreSQL.
  Таймаут SQL и ожидания соединения — 5 секунд.
- HTTP-слой — Django REST Framework: serializers для валидации, JSON-ответы и единый
  обработчик ошибок. OpenAPI и Swagger UI формируются через drf-spectacular.

## Проверки

Все проверки с настоящей PostgreSQL, включая конкурентное бронирование:

```bash
docker compose --profile test run --build --rm test
```

Локально:

```bash
poetry run ruff check .
poetry run ruff format --check .
poetry run python manage.py check
poetry run pytest -v
```

Без явного включения интеграционные тесты пропускаются. Для запуска с БД,
настроенной в `.env`, задайте `RUN_INTEGRATION_TESTS=1`:

```bash
export RUN_INTEGRATION_TESTS=1
poetry run pytest -v
```

В PowerShell: `$env:RUN_INTEGRATION_TESTS = '1'`. Для отдельной тестовой БД можно
вместо этого задать `TEST_DATABASE_URL` в окружении или локальном `.env`.

Каждый интеграционный тест создаёт отдельную случайную схему и удаляет только её
в конце; существующие таблицы приложения не затрагиваются. Рекомендуется отдельная
тестовая БД. Покрываются CRUD, сортировки, ошибки, високосные даты, точность цены,
каскадное удаление, все виды пересечения, соседние интервалы и восемь конкурентных
попыток забронировать один номер. GitHub Actions генерирует временный `.env`
со случайными секретами и запускает тот же Docker-профиль с Ruff и всеми тестами.
Постоянных паролей в CI-конфигурации нет.

## Структура

```text
manage.py           # Django management commands
app/settings.py     # Настройки Django, REST Framework и пула PostgreSQL
app/urls.py         # HTTP-маршруты и документация
app/views.py        # HTTP-хендлеры
app/serializers.py  # Валидация входа и сериализация ответов
app/models.py       # Django ORM-модели Room и Booking
app/db.py           # Операции ORM и транзакции
app/parsers.py      # JSON с Decimal и формы без дублирования полей
app/exceptions.py   # Единый формат ошибок API
app/wsgi.py         # WSGI-приложение для Gunicorn
db/schema.sql       # Таблицы, ограничения и индексы
tests/              # Тесты HTTP через WSGI и интеграция с PostgreSQL
compose.yaml        # API, PostgreSQL, профиль test
scripts/init_env.py # Создание локального .env со случайными секретами
```
